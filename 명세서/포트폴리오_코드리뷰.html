📐 설계 한 줄 요약
Editor는 저작(authoring), Runtime은 소비(consume) — Assimp/RTTR/ImGui/ImGuizmo는 전부 Editor에 격리되고, Engine/Client는 검증된 자체 바이너리 포맷만 읽습니다. 이 원칙이 모델·NavMesh·Scene·UI 전 영역으로 일관되게 이어집니다.

02 레벨 디자인

레벨은 CLevel(Engine 추상) ← CLevel_GamePlay(Client)로 구성되고, CLevel_Manager::Change_Level로 교체됩니다. 무거운 리소스는 CLoader 워커 스레드가 CoInitializeEx 후 프로토타입으로 미리 적재하고, 레벨은 그 프로토타입을 레이어 단위로 Clone·조립합니다.

GamePlay 레벨 조립 순서 — Initialize()

레벨 초기화는 데이터 로드 → 조명 → 레이어 조립 → 충돌 규칙 → 트리거의 결정론적 순서를 따릅니다. 각 단계는 SceneData를 SSOT로 참조합니다.

03 게임플레이 구현 — 기술 & 설계

상태머신 커널 — opaque _uint + Policy Table

Engine의 CStateMachine은 의미를 모르는 추상 커널입니다. action을 불투명한 _uint 키로만 다루고, priority·auto-return·cooldown·reject 규칙만 강제합니다. Client의 CPlayer_StateMachine이 CHARACTER_ACTION × STEP을 그 키로 매핑합니다.

Engine/StateMachine.cpp — Try_Transition (요지)
if (m_Rejects 에 (current→next) 존재)        return false;  // 명시적 거부쌍
if (NextPolicy.iPriority < CurrentPolicy.iPriority) return false;  // 낮은 우선순위 거부
if (m_CooldownRemaining[next] > 0.f)           return false;  // 쿨다운
// 통과 → 전이 + On_Transition(prev, next, bInitial) 발화

void On_ActionFinished() {            // 애니 종료(Notify) 시
   if (pending) Try_Transition(pending);   // 버퍼된 입력 우선 소비
   else if (policy.bAutoReturn) Try_Transition(policy.iReturnAction); // IDLE 복귀 등
}

정책은 CHARACTER_ANIM_TABLE_DESC(데이터 테이블)에서 일괄 등록됩니다. 덕분에 게임 코드는 "몇 번 애니 재생"이 아니라 "현재 상태에서 어떤 action을 시도"로 표현되고, 스킬 파라미터(반경·데미지·offset)까지 같은 테이블에 실립니다.

AnimNotify — 애니 타이밍과 게임플레이의 디커플링

애니메이션 키프레임에 박힌 ANIM_NOTIFY가 Animation::Tick_Notifies(wrap-aware)에서 발화되어 INotifyListener 사슬을 타고 전달됩니다. 공격 판정을 "프레임 수"가 아니라 "애니가 여는 시점"으로 다루는 것이 핵심입니다.

ATTACK_HITBOX_ON/OFFCOMBO_WINDOW_OPEN/CLOSEFOOTSTEP_L/R INVINCIBLE_ON/OFFTRAIL_ON/OFFDETECT_ON/OFF

Body → AnimController → Model → Animation이 Notify를 listener에게 pass-through 하고, 상태머신/Player가 무기 OBB 활성화·콤보 윈도우·i-frame·트레일을 켜고 끕니다. On_Transition에 강제 OFF 안전망을 두어 윈도우 누수를 차단합니다.

충돌 시스템 — Manager + Group Matrix

오브젝트끼리 직접 검사하지 않습니다. Collider가 매 프레임 자신을 Manager에 등록(AddRef)하고, Manager가 group matrix로 허용된 쌍만 검사한 뒤 Enter/Stay/Exit 콜백을 보냅니다. 오브젝트는 "내 collider가 무엇을 맞았는가"만 처리합니다.

Collision_Manager — prev/curr set diff로 상태 전이 도출
// Late_Update: Add_Collider(group, collider)  ← 매 프레임 등록 + AddRef
// Update    : 허용 group 쌍 N² 검사 → m_CurrPairs 채움
m_CurrPairs - m_PrevPairs  → OnCollisionEnter
m_CurrPairs ∩ m_PrevPairs  → OnCollisionStay
m_PrevPairs - m_CurrPairs  → OnCollisionExit   // 죽은 객체도 AddRef 유지로 안전 발화
// End_Frame : prev↔curr swap + collider list clear (Renderer와 동일 수명 패턴)

// 그룹: PLAYER_BODY · PLAYER_ATTACK · MONSTER_BODY · MONSTER_ATTACK · MAP_STATIC

HUD

04 에디터 구현 — 기술 & 설계

에디터의 설계 원칙은 단 하나, 격리입니다. Assimp·RTTR·ImGui·ImGuizmo는 모두 Editor 전용이고 Engine/Client는 이들을 전혀 모릅니다. Engine 측 훅은 최소화하여, 예컨대 ImGuizmo 연동은 CTransform::Set_WorldMatrix 인라인 setter 한 줄로 끝납니다.

ImGui 셸 + 패널 구조

CPanel(추상) ← 8개 패널, 모두 CPanel_Manager(singleton)가 관리합니다. 패널이 GameInstance/Manager를 Safe_AddRef 하며 생기는 순환 참조는 Release_Panels() 수동 해제(EditorApp::Free)로 끊습니다.

Editor = 게임 호스트

에디터는 별도 더미 씬이 아니라 Client 런타임을 직접 호스팅합니다(Edit/Play 토글). 같은 프로토타입을 Clone 해 같은 GameObject를 띄우므로, 에디터에서 보는 것과 GameApp 실행 결과가 동일한 런타임 객체입니다. Client 게임 레벨은 CLIENT_DLL export가 없어, Editor 전용 빈 셸 CLevel_Editor + Ready_TestScene()로 대체합니다.

🔌 폴링 기반 동기화의 선택
Inspector(RTTR getter)와 Gizmo가 각각 매 프레임 m_WorldMatrix를 폴링하므로, dirty 플래그나 이벤트 버스가 필요 없습니다. SSOT 하나만 정확하면 양방향 동기화가 자동으로 맞춰지는, "상태는 하나, 표현은 폴링" 전략입니다.

05 파일 저장 & 로드 관리 — 언제 / 어떻게

네 종류의 자체 바이너리 포맷이 있고, 모두 동일한 규약을 따릅니다: magic(4byte) + version + body, 공유 CBinaryWriter/CBinaryReader, 그리고 version 분기 + 누락 필드 fallback. 저장은 항상 Editor(저작), 로드는 항상 Runtime(소비) 시점입니다.

저장 / 로드 타임라인

✍️ 저작 시점 — Editor (명시적 Save)

저장은 항상 사용자가 버튼을 눌렀을 때 일어납니다. 자동 저장·암묵 저장이 없어, 무엇이 언제 디스크에 박히는지 추적이 쉽습니다.

  • Panel_Inspector → pModel->Save_Binary()
  • Panel_NavMeshEditor → Save_NavData() / Save_SceneData()
  • Panel_2DCanvas → UICanvasTool::Save()

▶️ 소비 시점 — Runtime (레벨 진입)

로드는 레벨 초기화와 로더 스레드의 정해진 순서에서만 일어납니다. 모델은 스레드에서 선적재, 데이터(scene/nav/ui)는 레벨 조립 중 로드.

  • 모델: CLoader::Loading() (워커 스레드, CoInitializeEx)
  • Scene/Nav: Level_GamePlay::Initialize 초반
  • UI: Ready_Layer_UI (레벨 조립 후반)

버전 호환의 실제 코드 — 깨지 않고 늘리기

포맷이 자랄 때 옛 데이터를 버리지 않는 것이 이 파이프라인의 약속입니다. 읽기 시 iVersion으로 분기하고, 신규 필드는 옛 버전에서 안전한 기본값으로 폴백합니다. (예: UIScene v7에서 추가된 sweep mode)

UISceneSerializer::Read_Element — version 분기 + fallback
if (iVersion >= 6) Reader.Read(&pOutElement->vColor);
else             pOutElement->vColor = {1,1,1,1};      // 구버전: 흰색 폴백

if (iVersion >= 7) {
    Reader.Read(&iSweepMode);
    if (iSweepMode >= END) iSweepMode = 0;     // 방어적 클램프
    pOutElement->eSweepMode = (UI_SWEEP_MODE)iSweepMode;
} else pOutElement->eSweepMode = NONE;            // 구버전: NONE 폴백
왜 JSON이 아니라 바이너리인가
저작 단계의 가독성은 Editor UI가 책임지고, 런타임은 크기·파싱 속도·의존성 0의 자체 바이너리만 읽습니다. magic으로 포맷 오인을 막고, version으로 진화를 허용하며, fixed-size WriteArray로 문자열 필드를 단순화했습니다. "편집은 도구가, 적재는 포맷이" — 1장의 저작/소비 분리 원칙이 직렬화 레이어에서도 그대로 반복됩니다.

06 코드 리뷰 & 총평

8주 · 96 커밋 · 약 33,000 LOC의 솔로 프로젝트로서, "기능 개수"가 아니라 "구조가 감당 가능한 순서로 자랐는가"를 기준으로 평가합니다.

강점

  • 일관된 의존성 방향 — 외부 라이브러리를 Editor에 완전 격리. Engine/Client는 자체 포맷만 소비.
  • 통일된 직렬화 규약 — 4개 포맷이 magic+version+fallback을 공유. 데이터 파이프라인의 성숙도가 드러남.
  • SSOT 규율 — Transform·Loop·Notify·NavMesh owner의 단일 소유를 정하고 나머지는 폴링/캐시.
  • 추상 상태머신 커널 — Engine은 opaque _uint만, Client가 의미를 매핑. 정책은 데이터 테이블.
  • 이벤트 기반 전투 — AnimNotify가 판정 타이밍을 열고 닫아 애니/게임플레이 디커플링.
  • 충돌 매니저화 — group matrix + prev/curr set diff로 Enter/Stay/Exit를 안전하게 도출.
  • 명시적 수명 관리 — CBase ref count와 문서화된 함정(Clone SRV AddRef 등)으로 D3D/DLL 경계 통제.
  • Decision Log 문화 — 번복된 결정까지 이유와 함께 보존해 추적성 확보.

개선 여지 (건설적)

  • God-object 경향 — CPlayer가 이동·전투·스킬·무기·QTE·텔레포트·바디블록 해소·콜라이더까지 ~50 멤버/~60 메서드를 보유. CHUD_GamePlay도 동일. Combat/Loadout/Skill 컴포넌트로 분리 여지.
  • Facade 표면적 — CGameInstance가 15개 서브시스템·~100 메서드를 노출. 편리하지만 변경 파급면이 넓음.
  • 충돌 broadphase 부재 — group 쌍 N² 검사. 현재 규모(1 Player + 소수 Monster)에선 충분하나 확장 시 공간 분할 필요.
  • 매직 넘버 / 하드코딩 튜닝 — cell index(40, 트리거 cell), 다수의 튜닝 float이 헤더 상수로 산재. 일부는 SceneData로 데이터화 가능.
  • dynamic_cast 다용 — Find_FirstPlayer/Boss가 매 트리거 프레임 레이어 순회+캐스팅. 캐싱 여지.
  • 인코딩 혼재 — 주석이 CP949/UTF-8 혼용으로 깨짐(문서화된 이슈지만 유지보수 냄새). 자동화 테스트 부재(솔로 게임플레이 특성상 수동 검증).

총평

한 문단 정리
이 프로젝트의 진짜 성과는 화려한 단일 기능이 아니라 "제작 루프가 도는 구조"를 만든 것입니다. Editor가 데이터를 만들고 버전형 바이너리로 저장하면, 같은 런타임 객체를 GameApp이 소비합니다 — 모델·NavMesh·Scene·UI 전 영역에서 이 한 가지 패턴이 반복됩니다. 상태머신은 의미를 모르는 커널로 추상화되고, 전투는 AnimNotify 이벤트로 디커플링되며, 수명은 명시적으로 통제됩니다. 남은 과제는 거대해진 게임플레이 클래스를 컴포넌트로 쪼개고, 매직 넘버를 데이터로 끌어내며, 검증을 자동화하는 것입니다. 즉 다음 단계는 새 기능이 아니라 이미 검증된 구조의 응집도를 높이는 리팩토링입니다.
포트폴리오 화법 한 줄
"게임 하나를 만든 것이 아니라, 게임을 만들기 위한 프레임워크와 저작 파이프라인을 직접 확장했고, 그 모든 결정의 이유를 기록으로 남겼습니다."
