## 4. 적용 우선순위

### 4.1 1차 적용: Culling / QuadTree

발표 전 우선 적용 대상.

| 순서 | 항목 | 원본 일차 | 목표 |
|---|---|---|---|
| 1 | Frustum Culling | 18일차 | 카메라 절두체 기준 오브젝트/맵 가시성 판정 API 확보 |
| 2 | Map Mesh Culling | 19일차 | `MapStaticObject` / `CModel` / `CMesh` 렌더 루프에 Frustum 판정을 연결 |
| 3 | Map Mesh QuadTree | 20일차 | 검토 후 보류. LOD/chunk 구조 없는 현재 실내형 model map 에서는 탐색 비용이 이득보다 클 수 있음 |

선정 이유:

- 추가 게임 리소스 없이 코드 중심으로 진행 가능하다.
- Boss VFX / Projectile 리소스 공백과 무관하게 진행할 수 있다.
- 발표에서 최적화 항목으로 설명하기 쉽다.
- 기존 Gameplay 로직과 직접 충돌할 가능성이 낮다.

주의:

- 수업 코드의 `Frustum`, `QuadTree`, `VIBuffer_Terrain` 구조를 그대로 덮어쓰지 않는다.
- 현재 프로젝트의 `Camera_Follow`, `Camera_Free`, `Renderer`, `MapObject`, `NavigationAgent` 구조와 맞춰 필요한 부분만 이식한다.
- 현재 프로젝트는 Terrain 렌더링을 실제 게임 맵에 사용하지 않으므로, 19~20일차는 `Terrain` 기준 구현을 `MapObject` / `MapStaticObject` / mesh 단위 culling 으로 재해석한다.
- `EngineSDK_Update.bat` 대상이 되는 Engine public header 변경은 적용 후 SDK 갱신 필요 여부를 확인한다.

## 8. 2026-05-22 결정 로그

### Frustum / Map Mesh Culling 적용

- 수업 18일차 `FrustumCulling` 을 기반으로 Engine `Frustum` 서비스를 추가했다.
- 수업 19일차 `Terrain_Culling` 은 Terrain 정점을 월드로 변환하지 않고, Frustum 을 Terrain local space 로 변환한 뒤 local vertex 와 비교하는 방식이었다.
- 현재 프로젝트는 Terrain 기반 맵이 아니라 `MapObject -> MapStaticObject -> CModel -> CMesh` 기반 `.bin` model map 을 사용하므로, 같은 개념을 mesh local bounds 기준으로 재해석했다.
- `CMesh` 에 mesh별 local AABB 를 캐싱하고, `CModel` 이 mesh index 기준 bounds 를 중계하는 구조로 정리했다.
- `MapStaticObject::Render()` 에서 Frustum 을 MapStaticObject local space 로 변환한 뒤, mesh bounds radius 기준으로 보이지 않는 mesh 렌더를 skip 한다.
- 디버그용 radius 조정으로 실제 culling 동작을 확인했다.
- FPS 는 `GameApp.cpp` main loop 에서 `_DEBUG` 창 제목에 표시하는 방식으로 검증한다.

### QuadTree 검토 후 보류

- 수업 20일차 `QuadTree` 는 Terrain grid 의 네 corner 정점 인덱스와 center 정점 인덱스를 들고, 자식 노드 4개로 재귀 분할하는 구조다.
- 이 방식은 정점이 X/Z 격자로 정렬되어 있고 LT/RT/RB/LB 인덱스 계산이 가능한 Terrain 에 적합하다.
- 현재 프로젝트의 일반 model mesh 는 정점 인덱스가 공간 격자 순서가 아니므로, 수업 QuadTree 를 그대로 mesh 정점에 적용하면 구조가 맞지 않는다.
- 대안으로 Mesh bounds 기반 QuadTree 를 설계할 수는 있으나, 현재 맵은 실내형 model map 이고 LOD/chunk/merged mesh 구조가 없다.
- 화면 안에 대부분 mesh 가 들어오는 상황에서는 node 탐색 + leaf 검사 비용이 추가되어 QuadTree 가 오히려 손해가 될 수 있다.
- 따라서 현재 마감 기준은 `Frustum + Mesh Bounds Culling` 까지로 확정하고, QuadTree 는 맵 규모 확대 또는 LOD/chunk 도입 시 재검토한다.

### Ready_Lights 현재 의도

- Directional Light 는 ThroneRoom 전체 톤을 잡는 전역 광원이다.
- PointLight 는 특정 위치의 횃불/장식/문 주변을 밝히는 국소 광원이다.
- Directional 하나로 모든 암부를 억지로 밝히지 않는다. 암부는 Ambient 로 완만하게 보정하고, 필요한 공간은 PointLight 로 보강한다.
- `Target_Specular` Preview 가 검게 보이는 것은 반드시 오류가 아니다. Specular 값, normal 방향, 카메라 방향, light 방향에 따라 거의 검게 보일 수 있다.
- 점광원 검증 시에는 일부러 강한 값으로 시작해 "반응 여부" 를 먼저 확인하고, 이후 실제 연출 값으로 낮춘다.

## 11. 2026-05-25 추가 결정 로그

### FMOD Sound Manager

- 수업 코드 후속 적용 순서상 Shadow/NormalMap으로 넘어가기 전에 FMOD 기반 사운드 인프라를 먼저 넣는 것으로 결정했다.
- Engine 소유 `CSound_Manager`를 추가하고, Client/GameApp/Editor는 `CGameInstance` 래퍼(`Play_Sound`, `Play_BGM`, `Stop_Sound`, `Set_SoundVolume` 등)만 사용한다.
- `<filesystem>` 의존은 프로젝트 표준 문제를 만들 수 있어 Win32 `FindFirstFile` 재귀 스캔 방식으로 정리했다.
- BGM/SFX 재생 연결까지 완료되었다. 이후 세부 사운드는 Level BGM → Player 공격/피격 → UI → Monster 순서로 콘텐츠별 확장한다.

### Camera_Cinematic

- Igris 모델에 실제 Camera animation이 없고 Pivot만 있으므로, `CCamera_Cinematic`를 별도 카메라 오브젝트로 두고 Pivot/월드 위치를 기준으로 Eye/At을 구성한다.
- 현재는 `FIXED`, `ATTACH_PIVOT`, `RAIL`, `PINGPONG` 모드를 가진 1차 범용 리그다.
- 아직 `CCameraDirector`나 Follow 복귀 blend 상태머신은 없다. 보스 Intro 등에서 직접 `Play_*`를 호출하는 사용처를 연결한 뒤, 필요하면 Director를 추가한다.

### Atlas Instance Effect

- 횃불 VFX는 PointLight 자체에 렌더 기능을 넣지 않고, SceneData의 `Torch_` PointLight 좌표를 별도 atlas billboard effect가 참조하는 구조로 분리한다.
- `CVIBuffer_Instance`/`CVIBuffer_Rect_Instance`는 수업 코드의 인스턴싱 흐름을 현재 Engine VIBuffer 구조에 맞춘 1차 이식이다.
- `CAtlasInstanceEffect`는 Torch 전용 이름을 피하고, texture prototype tag + positions + atlas info를 받는 범용 오브젝트로 둔다.
- 6x6 atlas는 균등 UV 분할로 시작하되, 셀 여백 대응을 위해 `vUVPadding`을 Desc에 포함했다.
- 실제 texture prototype 등록, `Level_GamePlay`의 `Collect_TorchLights` 기반 오브젝트 생성, additive blend/depth state 튜닝까지 1차 완료했다.


### 2026-05-25 Torch VFX 적용 완료 메모

- SceneData LightData에서 `Torch_` prefix를 가진 PointLight만 atlas billboard instance source로 사용한다.
- 일반 PointLight는 조명만 담당하고, Torch 이름을 가진 PointLight만 불꽃 VFX를 추가로 생성한다.
- `Shader_VtxRectInstance.hlsl`의 `Atlas_Instance` pass는 범용 alpha blend 용도로 유지한다.
- 불꽃은 `Atlas_Instance_Additive` pass를 사용해 black 근접 픽셀을 shader에서 discard하고 additive blend로 합성한다.
- 원본 fire atlas PNG는 유지한다. 검은 배경 제거는 텍스처 파괴 편집이 아니라 shader pass 정책으로 처리한다.
- Torch effect는 현재 6x6 균등 atlas, `vUVPadding`, `fFrameDuration`, `vSize`, `vColor`, `fAlpha`, `iShaderPass`로 조정한다.
## 10. 후속 작업자가 지켜야 할 경계

- C++/HLSL 을 무작정 수업 코드로 덮어쓰지 않는다. 현재 프로젝트에 이미 적용된 14일차 구조를 먼저 확인한다.
- 하지만 구조적 방향은 수업 코드가 기준이다. 없는 변수를 새로 invent 하기보다 현재 프로젝트의 `Engine_Enum.h`, `Renderer.cpp`, `Light.cpp`, `Shader_Deferred.hlsl` 가 수업 코드의 어떤 항목에 대응하는지 맞춰가며 진행한다.
- Debug Preview 좌표/크기는 검증 편의를 위한 값이다. 렌더 기능의 본질이 아니므로 과도하게 시간을 쓰지 않는다.
- Alpha discard 문제는 "셰이더가 틀렸다" 보다 "현재 추출 모델의 material alpha 가 수업 코드 예제와 다르다" 로 본다.
- PointLight Hardcode 는 임시다. 최종 설계는 SceneData / Editor 배치 기반이다.
- 다음 큰 렌더 작업은 수업 코드 순서에 맞춰 Shadow(16일차)를 먼저 검토하고, 이후 NormalMap(17일차)로 이동한다. 진행 전 Deferred 기본 흐름과 Torch additive effect 회귀 여부를 확인한다.
